# 反対方向 W1 出現後のプラス決済: 独立設計レビュー

対象は v1.50 の `Wave33VisualVerifier.mq5`、`Types.mqh`、`Ledger.mqh`、`Display.mqh`。このレビューではコードを変更していない。

## 判定の意味と時刻

- 初期設定の発火点は `WAVE1_PEAK_CONFIRMED` とする。現状で青い「① 第1波」を描くイベントと一致し、暫定のブレイク候補との意味を混ぜない。
- 保存すべきものは反対候補 ID、方向、W1 頂点の足時刻、頂点が確定した時刻、保有ポジションに対して決済待機を開始した時刻。決済は頂点の過去時刻では実行しない。
- 反対 W1 を認識した時点で、その保有取引の決済待機をラッチする。反対候補が後で Fib 超過などにより失効しても待機を解除しない。これは「出たら、その後プラスになった時点」という今回の指示の解釈。
- 保有後に発生したイベントだけが対象。既にあった反対 W1 を後から拾って、新しく保有した取引に適用しない。秒単位の同時刻イベントでは行順またはイベント連番も必要。`event_at > fill_at` だけでは同じ秒の後続イベントを落とすため、その限界を明記するかミリ秒時刻を保存する。
- 既存 SL / TP は待機中も有効。プラス復帰しなければ従来 SL、TP、テスト終了のいずれかとなる。待機開始は損切りを遅らせる理由にしない。

## ネイティブ注文の留意点

1. `DEAL_POSITION_ID` / `POSITION_IDENTIFIER` は追跡用識別子。実際の決済リクエストの `position` には、現在の `POSITION_TICKET` を設定する。識別子が一致する実ポジションを列挙して、銘柄、magic、方向も再確認する。チケットと識別子を同一と仮定しない。[公式 position properties](https://www.mql5.com/en/docs/constants/tradingconstants/positionproperties)
2. ロングの決済は Bid、ショートは Ask の現在の実行可能価格で評価する。元の注文時の価格やミッド価格は使わない。残存数量の値幅利益、既知の建玉コスト、保有スワップ、推定決済手数料を含めて、推定総損益が閾値を厳密に超えることを条件とする。閾値 0 なら損益ゼロは決済条件を満たさない。
3. 決済手数料は将来の実額を事前確定できない。既知の入口手数料からの推定と、入力による追加余裕などの採用方法をログに残す。スリッページによって実損益が負になる可能性と、推定プラス判定が正しかったことは区別する。決済後は全 deal の profit + commission + swap + fee の実額で R を計算する。
4. `OrderSend` が true でも約定完了を意味しない。リクエスト送信、受理、約定、最終終了を別イベントで保存する。`PLACED` や `DONE_PARTIAL` の間に同じ残数量を再送しない。[公式 OrderSend](https://www.mql5.com/en/docs/trading/ordersend)
5. 決済には残存数量、実チケット、逆方向売買種別、銘柄に対応する filling mode を設定する。部分決済後は実ポジションの残数量と進行中注文を確認してから、改めて利益条件を満たすティックで残りを決済する。FOK/IOC 不成立や拒否は記録し、保有を架空の CLOSED にしない。[公式 closing positions](https://www.mql5.com/en/book/automation/experts/experts_close)
6. 受理済み決済注文のまま SL / TP が成立する競合では、新たな反対建玉を作らない。決済待機の解除を単純なタイムアウトだけで判断せず、注文履歴・生存注文・実ポジションで確認する。取引トランザクションの到着順序は保証されない。[公式 OnTradeTransaction](https://www.mql5.com/en/docs/event_handlers/ontradetransaction)
7. ブローカーの `DEAL_REASON_EXPERT` と、戦略上の `OPPOSITE_WAVE1_PROFIT` を別項目にする。待機中に SL が先に約定した取引を、反対 W1 決済と表示しない。送信した決済注文 ID または request ID と実決済 deal を関連づける。
8. `MergeExecution` は戦略イベントの構造体を実行記録で上書きするため、新しい待機・損益・決済属性も保存／復元する。後続の Engine イベントで待機フラグや決済理由が消えないことをテストする。
9. 従来の main は deal の識別子による累計管理であり、部分約定を既に扱っている。追加機能が deal の金額や数量を二重計上しないこと、最終 EXIT が一度だけであることを確認する。

## 独立監査

- すべての待機イベントから反対候補を逆引きし、反対方向、同一銘柄・時間足、認識時刻、保有中だけの適用を検査する。
- 待機後の各評価ティックに `time_msc`, Bid, Ask, 残数量、既知累計コスト、スワップ、推定決済費用、推定 net、閾値、pending 状態を保存する。決済送信だけのログでは「最初のプラスティック」を独立検証できない。
- XAUUSD+ / USD 口座の有限比較なら、銘柄 contract size と保有平均価格から Python 側で線形利益を独立再計算し、entry cost / swap / exit cost estimate と加算する。口座通貨換算が必要な一般銘柄では、換算時刻とレートも別に必要。
- 各送信について直前の正の net と、その前に pending でない正のティックがなかったことを検査する。サーバー拒否・部分約定は初回送信と完了時刻を分離する。
- 実 deal を位置識別子でまとめ、入出数量整合、SL/TP/専用決済の理由、実 net / 当初 SL リスクの R、未決済テスト終了を再計算する。
- ハーネス最低項目: LONG/SHORT の正負・厳密ゼロ、Bid/Ask スプレッド、入口費用・決済推定費用・swap、反対 W1 前後、既存反対 W1 の非適用、反対失効後のラッチ継続、注文拒否、accepted pending、部分決済、SL/TP 競合、他 magic、ticket/identifier 相違、同秒の順序。
- 描画では①の位置とは別に「反対①認識・プラス待ち」を認識時刻から表示する。EXIT は実約定時刻・実価格に置き、ENTRY/SL/TP の履歴をその時点で閉じる。

このレビューは実装方針と検証要件であり、収益改善の主張ではない。
